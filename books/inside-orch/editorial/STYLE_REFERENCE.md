# Editorial style reference

The sample `samples/runtime-boundary.md` is a source specimen, not an executed laboratory. Its fifteen pinned source/history links resolve in the local immutable corpus; three focused listings match their pinned intervals after removing a common leading tab for display. `validation/intake/foundation-source-audit.json` records that actual static check. Display indentation is not a change to source bytes in the excerpt registry.

## The useful narrative shape

Start with a concrete interruption and an owner: a new server process, a lost report, an isolated worker. State what the reader will be able to explain or measure. Trace the actual composition root and caller before generalizing from a package. Use a short exact listing to expose one decision, then explain the failure window on both sides of it. Pair that explanation with a deterministic experiment and, separately, any external integration required for a stronger claim.

Use direct English, precise status names and a restrained number of tables. A useful comparison contrasts two real control paths or two observations with different meaning. Avoid generic platform introductions, repeated reliability slogans, empty chapter summaries and unexplained feature lists. The audience needs engineering decisions and evidence, not production-workflow instructions in the narrative.

## Evidence language

- **Source-inspected:** implementation/caller/test reviewed; no command result implied.
- **Expected:** source predicts this experiment outcome; execution has not established it.
- **Observed:** a specific command record, scope and log establish this result.
- **Teaching extension:** independently authored and tested outside immutable upstream source.
- **Design only / future work:** requested or proposed mechanism is not present as active behavior.

Use full baseline SHAs, real source intervals and known historical commits. A retrospective prompt is intent evidence rather than proof of chronological execution. Do not transfer a unit-test assertion to a distributed guarantee, a fixed ready response to durable recovery, or declared policy fields to Docker enforcement.

## Chapter acceptance

Each chapter uses its frozen title and native H1 syntax; explains its distinct problem/outcomes, source/caller path, chapter-specific failure timeline, safe Atlas experiment, three to five progressively harder exercises and separate worked answers. Store exact listings with extraction metadata, complete claim records and a chapter review. Narrative length is 1,800–2,500 meaningful words excluding code/commands/metadata; this is a comprehension budget rather than a quota filled by repeated boilerplate.

Keep exercises specific enough that an unsafe assumption can be falsified. Answers must explain why the source or experiment supports the decision. A missing Docker/database gate remains visible; a useful source-only analysis may proceed while release integration remains blocked. Never repair the application baseline to make an answer true.

## Continuing sequence

Write stable chapters 01–40 using frozen contracts and case-study identity `atlas-api`; consult dependency order in READER_PATHS when running experiments. Preface is section zero, appendices A–F follow chapters, answers are companions. Return to capability IDs and observation/failure contracts when terminology or integration claims are disputed. Later semantic/security/editorial review can revise book prose, but it cannot silently change source revision, license or executed evidence.

## The promise

Teach developers how to read and evolve orchestration code, DevOps engineers how to operate and diagnose its real executable behavior, and architects how to reason about guarantees, composition, persistence, isolation, and failure. The book follows one inspectable Go/Docker system through its actual history. It does not turn a feature checklist into a production claim.

The source of truth is `evidence/orch/` at the full SHA in `evidence/source-lock.json`. The source corpus has 91 numbered development prompts, 105 reachable commits, 16 migration pairs, and a default server based on `MemoryService`. Chapter outlines and commit relationships are supplied, but must be verified again during writing. Do not change the baseline midway through the book. ## Required chapter form

1. State the operational or design problem, prerequisites, and learning outcomes.
2. Explain the current implementation using a focused source walkthrough, exact symbols, and short listings.
3. Connect the original development prompt to actual implementation evidence, including real commit links. Explain batched or retrospective associations.
4. Identify the invariant and a specific failure window. Separate what a library proves from what the executable integrates.
5. Include an experiment with prerequisites, commands verified against source, observations, cleanup, and evidence criteria. Label expected results until actually run.
6. Add three to five progressively harder exercises. Store worked answers separately, with tests or reasoning that justify them.
7. End with concrete engineering decisions, current boundaries, and source references; avoid generic chapter summaries.

Store chapter prose in `manuscript/chapters/`; appendices in `manuscript/appendices/`; answers in `manuscript/solutions/`; chapter claims in `validation/evidence/chNN.json`; lab logs in `validation/labs/`. Use the supplied templates. Every factual engineering claim must be linked to source, experiment, or an explicitly labeled inference.

## Capability classification

Use these labels consistently: **runtime-integrated**, **implemented package**, **partial integration**, **design only**, **teaching extension**, **future work**. An implemented package can be unit-tested and still be absent from a binary. A runtime-integrated path may still have serious limits. Tests and production claims require their own evidence.

Non-negotiable boundaries to verify and explain:

- The default server uses live in-memory state; PostgreSQL tables and backup scripts do not make that state durable.
- Scheduler package planning and normal MemoryService service placement have different paths. Trace both before describing placement guarantees.
- Resource admission/accounting and Docker enforcement are different. Trace fields through API agent DTOs and ContainerSpec.
- Leadership and autoscaling packages are not automatically active server controllers.
- A restart test that reuses a MemoryService instance demonstrates a controller restart, not process or database durability.
- Signing/scanning, advanced networking, plugins, billing and stateful scheduling must be labeled by their actual implementation scope.
- A supplied image digest is different from network resolution of a mutable tag to a digest.
